# 합성 식별자 안전성 점검과 안전 픽스처 방식

공개 저장소에 올리는 `train/val/test.jsonl` 은 **안전 픽스처**이고, 유효한 전체 식별자가 있는 원본은 `apps/api/data/private_eval/baseline_v2/` 에만 만든다(`git check-ignore` 로 `apps/api/data/` 가 무시됨을 확인함). 생성기는 공개(`build_baseline_v2.py --profile safe|private|both`)이며 같은 틀·분할·라벨에 값만 다르게 만든다.

## 1. 기존(원본) 생성기의 값 분포와 위험 (private 프로필 실측)
| 종류 | 분포(실측) | 실존 값과 겹칠 위험(추정) |
|---|---|---|
| 주민번호 | 84개 중 생년월일이 달력상 유효 64, 체크섬 유효 64(의도한 체크섬 실패·월일 오류 20씩 제외), 성별 자리 1~4, 출생연도 1955~2012 | **높음~중간**. 현실적인 날짜·성별에 체크섬이 맞는 값이라 우연히 실제 사람의 번호일 수 있다. 하루·성별당 실제 출생자가 수백~천 명이고 뒤 5자리(지역·순번)가 10^5 공간이므로, 값 하나당 대략 0.1~수 % 로 어림한다(이론 추정, 측정 불가). 64개면 겹침이 한 건 이상 있을 수 있다 |
| 카드 | 84개 중 Luhn 유효 44(나머지는 의도한 Luhn 실패·OCR·오타), 16자리 72, 시작 4/51~53 | **낮음**. 16자리 10^15 공간에 실제 발급 카드는 10^8~10^9 수준(값당 약 10^-7~10^-6 어림). 유효기간·CVC 없이는 쓸 수 없다 |
| 전화 | 휴대 010-NNNN-NNNN 임의, 010 이 79/136 | **높음**. 010 임의 8자리(약 8천만 조합)는 상당수가 실제 가입된 번호일 수 있다(어림 수십 %). |
| 계좌 | 은행 형식을 흉내 낸 임의 숫자 76개 | **낮음~중간**(어림 값당 0.1~1 %). 은행별 자릿수 공간이 작을 수 있다 |
| 이메일 | example.com/org/net 만 | 없음 |
| 이름·주소 | 성+이름, 실제 도로명+임의 번호 조합 | 이름은 우연히 실존 인물과 같을 수 있으나 단독 식별정보는 아님. 주소는 공개 지번이 존재할 수 있음(잔여 위험) |

## 2. 안전 픽스처 방식 (공개 저장소 세트)
1. **주민번호**: 출생 2030년 이후(성별 자리 3/4, YY 30~99)만. 아직 태어나지 않은 날짜라 실존할 수 없다. 체크섬은 맞게 계산해 두었다(형식 검증 규칙 유지). **탐지기가 받아들이는지 확인함**: `_rrn_date_ok` 는 성별 3/4 이면 2000+YY 로 달력만 보므로 `normal_rrn` 20/20 모두 탐지(시험 `test_detector_accepts_safe_future_rrn`). 단 성별·연령 분포가 달라 탐지기에 연령 규칙이 생기면 편향이 생길 수 있다.
2. **카드**: 결제사 공개 문서에 시험용으로 실린 PAN(Visa 4111…1111, 4242…4242, 4012…1881, 4000…5556, 4000…0002, Mastercard 5555…4444, 5105…5100, 5200…8210, 2223…3222, Discover 6011…1117·6011…9424, JCB 3566…0505·3530…0000) 중 Luhn 을 통과하는 13개만. Luhn 실패·오타 사례는 이 PAN 의 한 자리를 바꾼 값 중 **Luhn 이 실패하는 것만**(Luhn 유효한 15자리 34/37 시작 거부). 이 목록은 공개 문서에 흔한 값이라는 내 기억에 근거하며 이번에 외부 대조는 하지 않았다(Luhn 은 코드로 검증).
3. **전화**: 방송·창작용 가상번호 범위를 **확인하지 못했다**(웹 검색에서 확인 불가). 그래서 가운데 블록을 `0000`으로 고정한 010-0000-NNNN(+82-10-0000-NNNN, 유선은 지역번호-000-NNNN)을 쓴다. 이 대역이 미배정이라는 것도 확정하지 못했으므로 **위험 낮음(추정)·잔여 위험 있음**으로 보고한다. 기관 대표번호(PHONE_PUBLIC)는 원래 공개 번호다.
4. **계좌·그 밖의 임의 숫자**: 계좌는 임의 숫자라 **잔여 위험이 남는다**(값당 0.1~1 % 어림, 개인 이름과 연결되지 않아 영향은 작음). 이메일은 `example.com/org/net` 만.

검사: `scripts/eval_pii_v2.py` 가 공개 세트를 읽을 때 `check_fixture_safety` 를 실행해 위 규칙을 어기면 중단한다. 시험(`test_baseline_v2.py`)은 안전 세트가 규칙을 지키는지, private 프로필이 규칙을 어기는지(= 검사가 작동하는지), 코드와 jsonl 이 일치하는지를 확인한다.

## 3. 안전 픽스처 vs 원본의 측정값 차이 (같은 탐지기, mapped·overlap)
- 전체 재현율 0.506(안전) vs 0.511(원본), 정밀도 1.000 vs 1.000. 거의 같다.
- 차이가 큰 곳: `odd_space` 재현율 -0.058(n=52; 원인은 확인하지 않음. 값 모양 차이로 추정), `card_typo` -0.050(n=20), PHONE -0.019, CARD -0.012. 주민번호·계좌·이메일은 0.
- 해석: 값 분포 차이로 인한 편향은 이번 탐지기에서는 작다(최대 5.8 %p, 문장 수 20~52). 다만 앞으로 값 분포를 활용하는 NER·분류기를 학습시키면 안전 세트(0000 전화, 미래 주민번호, 고정 시험 PAN)에서 학습한 모델이 원본 분포로 일반화하는지 별도로 봐야 한다.
