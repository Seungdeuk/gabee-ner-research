# 개인정보 탐지 평가 (PII Evaluation)

가족 채팅 AI(요약·일정/할 일 추출·답장 추천)가 외부 LLM 으로 보내는 대화에서 개인정보를 줄이는 가명화 파이프라인(`apps/api/app/shared/privacy/`)의 **탐지기**를 합성 한국어 데이터로 잰 결과다. 이 문서는 탐지기만 평가한다. 실제 AI 호출은 하지 않았다.

자유 글·JSON API(`prepare_text`·`prepare_json`)도 같은 탐지기(`detect`)를 쓰므로 아래 탐지 성능이 그대로 적용된다.

> 이 파이프라인은 종단간 암호화(E2EE)가 아니다. 서버는 DB 원문을 읽고, 외부 LLM 으로 나가는 글자에서 개인정보를 **줄일 뿐**이다. 아래 수치는 이 합성 데이터에서의 값이며 실제 대화에서 같은 성능을 보장하지 않는다.

## 데이터셋 (두 세트)

| 세트 | 파일 | 누가 썼나 | 성격 |
|---|---|---|---|
| 학습형 세트 | `eval/pii_eval.jsonl` (생성기 `build_dataset.py`, 시드 고정) | 규칙을 만든 쪽 | 템플릿 + 직접 쓴 문장. 규칙을 고치면서 계속 본 데이터라 **과적합 가능**, 수치는 낙관적이다 |
| 독립 보조 세트 | `eval/pii_eval_holdout.jsonl` (생성기 `build_holdout.py`) | **독립 검토자**가 따로 쓴 가족 대화체 81문장 | 검토 결과를 반영해 규칙을 고쳤으므로 더는 '처음 보는 데이터'가 아니다. 그래도 학습형 세트보다 현실에 가깝다 |

- 한 줄 형식: `{id, text, spans:[{kind,start,end}], known_names:[...]}`
- **모든 값은 합성이다.** 난수로 만든 값(카드는 Luhn, 주민번호는 체크섬이 맞거나 일부러 틀리게)이고, 실제 개인정보를 쓰지 않았다. 다만 난수라서 **실존하는 번호와 우연히 일치할 수 있다**. 이메일은 예약 도메인(`example.com/org/net`, `.test`, `.example`)만 쓰고(시험이 검사한다), 이름은 흔한 이름을 조합한 가상의 값이다.
- 학습형 세트: 양성 종류별 20개 이상(전화 휴대폰/유선/+82/구분자 변형, 이메일, 주민번호 유효·무효 체크섬, 카드, 계좌, 비밀 정보 표현, 주소 도로명/지번/동호수, 이름 사전/호칭), 음성 80개 이상(날짜·시간·금액·수량·주문번호·층수·일반 숫자·지명·일반 명사).
- 독립 보조 세트: 오탐 유발 문장(운송장·주문번호·'국민 10명'·'카카오택시'·'하나님'·'올레길 7코스' …)과 미탐 유발 변형(대시·전각·공백 구분, 키워드와 떨어진 비밀번호 …)이 많다. 양성 42 / 음성 39 문장이라 종류별 표본이 작다(4~14개). 수치의 오차가 크다.
- **의도적으로 남긴 어려운 사례**: 한글 숫자 전화번호("공일공 …"), 숫자 중간 공백, 말로 풀어 쓴 이메일, 붙여 쓴 주소, 사전에 없고 호칭도 없는 이름, 공백 구분 계좌, 키워드와 떨어진 비밀번호. 놓치는 것이 정상이며 한계를 드러내려는 것이다.
- 한계: 두 세트 모두 실제 가족 대화(구어체, 오타, 줄임말)가 아니다.

## 평가 방법

- 실행: `cd apps/api && PYTHONPATH=. python scripts/eval_pii.py [--set main|holdout|all] [--json | --md] [--write docs/security/PII_EVALUATION.md]` (외부 호출 없음)
- 일치 기준: **종류가 같고 겹침 비율(IoU) ≥ 0.5**. 엄격 일치(시작·끝이 같음)도 함께 낸다.
- 지표: 종류별 Precision / Recall / F1, 종류별 누락률(= 놓친 정답 / 정답), 음성 문장 오탐률(개인정보가 없는 문장에서 무언가를 찾은 비율), 처리 속도(평균은 데이터셋 문장, **최악 조건은 반복 입력 10만 자**).
- 평가 데이터를 규칙에 맞춰 고치지 않았다. 점수가 낮던 항목은 규칙을 고쳤다(아래 "개선한 것"). 독립 보조 세트는 검토 결과를 보고 규칙을 고쳤으므로 학습형 세트와 같은 의미의 낙관 편향이 일부 있다.

## 개선한 것 (평가·독립 검토 중 발견한 문제)

처음 버전 -> 독립 검토(81문장, 오탐 18 / 미탐 20) 후:

- **정규식 폭주(ReDoS)**: 응답 토큰 복원 정규식이 공백 `n` 개에 `O(n^3)` 이었다(`"[PHONE" + 공백×4000 + "_"` 38초). 길이 32자 이하 괄호만 후보로 잡고 안쪽은 코드로 검사하도록 바꿔 10만 자에 0.5 ms 가 되었다. 이메일 정규식도 `@` 없는 긴 영숫자에서 `O(n^2)`(숫자 4만 자 2.1초)이던 것을 시작 위치 조건으로 선형화했고, 겹침 정리(`_resolve`)는 이진 탐색으로 `O(n log n)` 이 되었다. 반복 입력 20만 자(숫자·하이픈·점·공백·한글·키워드) 모두 0.35초 이하이고 크기에 선형이다.
- **계좌 문맥**: 은행 이름만으로는 문맥이 되지 않는다('우체국 택배', '카카오택시', '국민 10명'). '은행·뱅크·계좌·입금' 같은 말과 함께거나 숫자 바로 옆에 붙어 있을 때만 인정하고, 운송장·주문번호·예약번호 단어가 가까우면 제외한다.
- **차단 임계값**: 정책에 `block_min_score`(0.7)를 넣어, 점수가 낮은 고위험 후보(구분 없는 13자리 숫자, 문맥 없는 카드 모양 16자리, 체크섬 불일치 주민번호)는 메시지를 차단하지 않고 값만 가린다. 난수 숫자 5,000개당 차단율: 13자리 8.4% -> 0.4%, 16자리 5.2% -> 0.0% (임계값 0 으로 되돌렸을 때와 비교, '번호 N 이야' 문맥; 운송장 문맥은 5.6%/9.6% -> 0.0%).
- **이름 별칭**: '김하나 -> 하나'처럼 이름만 부르는 별칭을 자동으로 만들 때 일반어 목록('하나·수정·지원·보라·나은 …')은 제외한다. 전체 이름 일치는 항상 허용.
- 호칭 휴리스틱 불용어 보강(하나님·박사님·형수님·목사님 …), 주소 오탐('올레길 7코스', '산책로 2바퀴', '서울 대도시', '3동 2호선'), '비번 wifi 랑 같아', '중구·동구 …' 2글자 구, 조사 '네'(민수네), 엔대시·전각 숫자·`010)`·`010/` 구분 전화, `900101 - 1234567` 공백 주민번호를 반영했다.
- (1차 평가) 지번 규칙이 "예약하려면 02-748" 을 주소로 잡던 문제, 13자리 숫자가 우연히 Luhn 에 맞아 카드로 잡히던 문제, "한강로 3가", "pin번호 2580", "010 - 1234 - 5678", "이영희씨고" 도 고쳤다.

## 알려진 한계 · 오탐/미탐 사례 (고치지 않은 것)

- **이름**: 가족 구성원 사전에 없고 호칭도 없는 이름("철수한테")은 찾지 못한다. 띄어 쓴 이름("김 민수"), 별명, 외국 이름도 놓친다. 이름과 호칭 사이의 공백 1칸("홍길동 선생님", "김철수 씨", "박영희 님께")은 잡도록 고쳤다(공백이 있는 '군'·'양'과 '사용자 님'·'모두 님' 같은 역할·직함 말은 제외). 평가 세트에는 이 꼴이 없어 수치는 그대로이고(두 세트 음성 오탐 0/114, 0/39 유지, PERSON 학습형 P 1.00 / R 0.882, 보조 P 1.00 / R 0.929), 대신 모듈 시험(`tests/test_honorific_alias.py`)에서 양성 4개와 일반어 음성 13개를 확인한다. 이름이 일반어와 같고 목록에 없는 경우("나래", "하은"이 일반어로 쓰일 때)는 오탐이 날 수 있다. 사전의 2글자 별칭("민수")은 이름만 부르는 말도 가리는데, 설계 검토에서는 '조사가 붙은 경우만'을 제안했으나 "민수 전화…" 같은 흔한 쓰임을 놓치게 되어 **일반어 목록 제외만** 적용했다(목록 밖 일반어와 같은 이름은 오탐 가능). 엄마·아빠 같은 가족 호칭은 이름이 아니므로 가리지 않는다. "김과장님"처럼 성+직함은 이름 꼴이라 가려진다(의도).
- **주소**: 건물 이름·약식 표현("강남역 3번 출구 앞 빌라 302호")·붙여 쓴 주소는 놓친다. 지명만 있는 "서울", "강남역"은 주소로 보지 않는다.
- **숫자**: 한글 숫자("공일공"), 숫자 중간 공백·오탈자, 공백으로 구분한 계좌번호("110 123 456789"), 문맥 없이 적은 계좌번호, 일부를 `*` 로 가린 주민번호, 앞뒤를 나눠 적은 주민번호는 놓친다. 주문번호가 우연히 전화·카드 규칙에 맞으면 오탐한다. 대표번호(1588-…)는 개인정보로 보지 않는다.
- **이메일**: `kim @ example.net`(공백), 최상위 도메인 없는 `kim@example` 은 놓친다.
- **비밀 정보**: 키워드("비밀번호", "인증번호", "PIN" …) 바로 뒤에 값이 오는 꼴만 본다. 값이 키워드와 떨어져 있거나("인증번호 왔어? 482913") 4자 미만이면 놓친다. 키워드 없이 적은 비밀번호도 찾을 수 없다.
- **주민번호**: 형식(실제 있는 생년월일 + 구분 1~8)이 맞으면 체크섬이 틀려도 잡되, 점수를 낮춰(0.45~0.6) 차단하지 않고 가리기만 한다. 체크섬이 맞는 번호만 차단한다.
- 사진·첨부 이미지, 건강 정보 같은 의미 기반 민감정보("당뇨 약 먹어")는 이 탐지기의 범위 밖이다.
- 학습형 세트의 F1 0.98 은 규칙을 이 데이터에 맞춰 다듬은 결과를 포함한다. **현실 성능으로 읽지 말 것.** 독립 보조 세트의 표본은 종류별 4~14개라 오차가 크다.

## 비교 실험(A/B/C 조건 AI 비교)

원문 / 마스킹 / 차단+마스킹 조건에서 AI 결과 품질을 비교하는 실험은 **스크립트 준비 단계이며 이번에 실행하지 않았다**. 실제 Anthropic 호출은 하지 않았고, 이 문서의 수치는 탐지기 평가만이다.

## Presidio 검토 결과

Microsoft Presidio 를 검토했으나 도입하지 않았다. 확인한 일반적 사실과 확인 못한 것을 구분한다.

- 일반 사실: Presidio 는 정규식 기반 recognizer 와 NER 모델(기본 spaCy)을 조합하는 구조이고, 기본 제공 recognizer 는 영어·미국 중심이다. 한국어 NER 은 기본으로 제공되지 않아 한국어 이름·주소는 별도 모델이나 직접 만든 recognizer 가 필요하다. 그러면 결국 대부분이 정규식 recognizer 가 되고, spaCy 등 의존성이 무겁다.
- 이 프로젝트 판단: 새 의존성 추가 금지 방침과 위 이유로 표준 라이브러리만 쓰는 자체 모듈을 만들었다.
- **확인 못함**: 최신 Presidio 버전의 한국 관련 recognizer(주민번호 등) 포함 여부와 성능, 한국어 spaCy 모델과의 정확한 연동 방법·성능은 이번에 설치해서 확인하지 못했다.
