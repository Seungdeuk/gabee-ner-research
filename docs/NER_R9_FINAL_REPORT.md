# NER R9 연구 최종 보고서

작성일 2026-11-19. 대상: 서비스 모델 `koelectra-small-v2b`(ONNX 지문 `46210943c45f`) 대비 R9 후보 F-full 시드 13.
**결정(사용자, 2026-11-19)**: 이번 실험은 독립 평가셋에서 PERSON 노출률과 Exact F1 의 실질적 개선을 입증한 연구 결과로 확정한다. 사전 등록 교체 권고 조건 5번이 D1P 유형의 노출 악화(+4.0%p)로 불충족되어 **운영 모델 교체는 승인하지 않는다.**

> **수치 구분 원칙**: 이 보고서의 "개발셋" 수치(소비된 5개 합성 평가셋, 후보 선정에 사용)와 "독립 평가셋" 수치(봉인 R9 v1.2, 1회 평가)는 서로 다른 평가이며 직접 비교하지 않는다.

## 1. 목적과 배경

- 목적: 가족 대화 NER(가명화) 모델의 이름(PERSON) 노출, 특히 메신저체 완전 미탐을 줄이면서 비PERSON 오탐과 과잉 병합을 악화시키지 않고 Exact F1 을 높인다. 사용자 목표는 전체 노출 5% 미만, 비PERSON 오탐 5% 이하, Exact F1 90% 이상.
- R8 의 일반화 실패: R8 후보는 개발셋에서 5시드 모두 서비스 모델보다 노출이 크게 낮았지만(매크로 6.53%→시드 평균 2.89%) 봉인 평가셋 new180 에서는 13.6%→14.6%로 서비스 모델과 같은 수준이었다(`NER_R8_RESULTS.md`). 개발셋 개선이 독립 평가셋으로 이어지지 않았고 그 이유는 확인하지 못했다.
- R9 의 접근: (1) 학습 데이터 작성자(Claude)와 독립 평가셋 작성자(ChatGPT)를 분리하고, (2) 학습 데이터 보강 효과를 라벨 정책 변경 효과와 분리하는 대조군을 두고, (3) 후보 선정 규칙·게이트를 평가셋 열람 전에 사전 등록했다(`NER_R9_PREREGISTRATION.md`).

## 2. 학습 데이터 설계와 정책 재라벨링

- **정책 r9-1.1**: `이름+가족호칭`은 이름 부분만 PERSON(호칭·조사·접미 `이`는 구간 밖), PERSON_ALIAS 는 별명 자체만, 별명/일반 명사 동형은 사람 문맥에서만 라벨, 호칭만 있는 문장은 음성, 1글자 이름은 연구 제외.
- **기존 데이터 재라벨**: 기존 학습 4,689행 중 292행(PERSON_ALIAS 구간)을 새 정책으로 재라벨(원본 보존, 전후 로그, 0행 격리).
- **신규 데이터**: 문형 틀 1,219개(Claude 하위 에이전트 작성, 6개 파일)에 이름·별명·호칭·단어를 채운 합성 문장 F-full 3,126행(전체 학습의 40%): 메신저 1,876(60%)·오류 유형 A/B/D 782(25%)·혼합 468(15%). 별도 검증 844행은 학습과 이름·틀이 겹치지 않는 모니터링 전용. 검증 문제 0건, 문장 중복 0건, 학습·검증 이름 겹침 0건.
- **격리**: 봉인·개발셋·기존 학습·규격 예시와의 겹침은 프로그램 안에서만 걸렀고(건수만 기록) 걸러진 후보는 개발 틀 1건, 예시 문자열 9건이었다. 봉인셋 내용은 생성·선택·튜닝에 쓰지 않았다.

## 6. 악화와 한계가 있는 항목

- **D1P 악화**: 노출 16.0→20.0%, Exact F1 89.1→73.3%. 50구간 중 2건 차이의 소표본이라 통계적 근거는 약하지만 사전 등록 규칙은 점추정(+2.0%p 초과 불가)을 보므로 조건 5 불충족. 원인 분석은 하지 않았다(봉인 평가 후 모델 수정 금지).
- **C2 Exact F1 하락**: 노출은 35.0→12.5%로 개선되었으나 Exact F1 은 10.5→3.4%로 하락했다. 보호는 개선되고 경계는 더 어긋난 유형이며, 노출과 Exact 를 분리해 해석해야 한다.
- **부분 노출**: 대표에서 6.10→5.19%로 거의 줄지 않았다. 개선의 대부분은 완전 노출 감소(14.03→6.10%)다.

## 8. 한계

- **합성 데이터**: 학습·개발·독립 평가셋 모두 합성 문장이다. 학습 신규 데이터는 문형 틀 1,219개(LLM 작성)로 문체 균질성 위험이 있고, 한 이름이 최대 34회 재사용된다(상위 3개 값 34·32·32회, 이름 값 2,602개 중 2,384개는 1회).

## 9. ACCOUNT 보안 점검 (기존 집계와 서비스 코드만 사용, 봉인셋 재평가 없음)

- **집계**: 대표 ACCOUNT 정답 62건 중 40건 BLOCK, 22건 노출, 스트레스 12건 중 10건 BLOCK, 2건 노출. 서비스 모델과 후보가 동일하다(NER 은 ACCOUNT 를 만들지 않는다. Exact 재현율 대표 64.5%, 스트레스 83.3%, 정밀도 1.0).
- **"노출"의 평가상 정의**: 정답 계좌 구간의 글자가 하나도 PERSON 계열이 아닌 **어떤 마스킹으로도 가려지지 않았고 해당 문장이 BLOCK(점수 ≥ 0.7) 되지도 않은** 경우. 즉 계좌 탐지 자체가 없었던 경우다(`value_masked` 0건, 낮은 점수 강등 사례 없음).
- **정책과의 불일치 여부**: **불일치 없음.** 정책 표는 ACCOUNT=BLOCK 이고(`policy.py`) 탐지되면 점수 0.7 이상에서 차단된다. 문제는 정책이 아니라 규칙 탐지 재현율이다. 규칙은 10~14자리 숫자에 은행명·`계좌`·입금류 문맥이 20자 이내에 있어야 계좌로 본다(`detectors.py`). 평가셋 정의("계좌 숫자열만", 문맥 요건 없음)보다 서비스 규칙이 좁다.
- **외부 LLM 전달 가능성**: 탐지되지 않은 계좌번호는 가명화 계층(`prepare_transcript`/`prepare_text`/`prepare_json`)에서 변경되지 않으므로 **원문이 외부 모델로 나갈 수 있다.** 새로 쓴 가상 문장 19건으로 현재 서비스 코드를 점검(`probe_account_rules.py`, 봉인셋 미사용)한 결과:

| 구분 | 결과 |
|---|---|
| 탐지·BLOCK, 원문 남지 않음 | 은행명 동반 11~13자리 하이픈형, `계좌` 동반, 입금만 동반(점수 0.7), 붙인 13자리+계좌, 엔대시·전각 숫자, 은행명이 번호 뒤, 카카오·토스뱅크, 한 문장 두 계좌 |
| **탐지 못해 원문이 남음** | 문맥 없는 하이픈 번호, 9자리 번호, 공백으로 구분된 번호, 문맥이 20자보다 먼 경우, `주문번호` 근처, 15자리 |
| 우연 보호 | 문맥 없는 붙인 13자리는 RRN(0.45)으로 오인되어 `[RRN]` 으로 가려짐 |

  독립 평가의 22건 노출은 이런 문맥 부재·형식 범위 밖 유형으로 추정되나, 어떤 유형인지는 봉인 정답을 열어야 알 수 있어 확인하지 않았다(추정이다).
- **운영 코드 기준 보호 조치**: 업로드 문서 경로는 별도 마스킹(`ingest/masking.py`, 계좌 라벨 정규식 포함)이 있어 채팅 경로와 규칙이 다르다. 채팅·어시스턴트 경로의 계좌 보호는 위 규칙 재현율에 의존한다.
- **필요한 회귀 테스트(제안, 코드는 변경하지 않음)**: (1) 공백 구분·9자리·15~16자리·먼 문맥·`주문번호` 근처 케이스의 기대 동작을 정하는 탐지 테스트, (2) 계좌 아닌 번호(주문번호·전화·운송장)가 새 규칙으로 계좌 판정되지 않는 오탐 회귀 테스트(기존 `test_hardening.py` 확장), (3) 게이트웨이 수준에서 `prepare_text`·`prepare_transcript` 결과에 원본 숫자열이 남지 않는지 검사하는 테스트. 재현율을 높이면 오탐(주문번호 등)과 맞바꾸게 되므로 규칙 변경 여부와 범위는 보안·제품 판단이 필요하다. 이 보안 항목은 R9 모델 결과와 별개로 서비스 규칙 계층의 후속 과제다.

## 10. 미해결 문제와 후속 연구 과제 (R10 등 별도 실험, 새 독립 평가셋 사용)

1. D1P·C2 유형의 악화 원인 분석과 처리(개발용으로만, R9 봉인셋은 소비됨).
2. 부분 노출(이름 뒷글자 경계) 감소, 신규 이름 일반화, 스트레스 세트 오탐.
3. 정책 단독 효과가 노출을 악화시키는 이유 규명.
4. ACCOUNT 규칙 재현율(§9)과 회귀 테스트.
5. 무작위성이 증명된 새 독립 평가셋과 사전 등록으로 별도 설계.
